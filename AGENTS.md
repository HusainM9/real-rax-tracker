# Project safety rules

## HTTP 5xx: stop, never repeat

Owner instruction, October 30, 2026, clarified to cover the whole 500 range: anything returning HTTP 500–599 must not be repeated. Be passive; do not reproduce failures against live services.

- Never retry or reissue a request that has returned any HTTP 5xx status (including 500, 502, 503, and 504), automatically or manually. Do not run it again to reproduce, benchmark, or verify the error.
- Do not evade this rule through a fallback, changed parameters, a fresh import, pagination, another account/session, a later scheduled job, or another deployment. Stop the affected operation and report the failure.
- Apply the rule to every dependency, including Real, Supabase, hosting and our own APIs. Preserve the original status through wrappers and partial-failure handling. An upstream 5xx must not become eligible for retry just because our route exposes a different status or a 200 response containing failures.
- Diagnose using existing redacted logs, source code, and offline fixtures only. Do not record credentials, cookies, session tokens, or private response bodies in reports.
- A successful test using mocked responses is not permission to repeat a known failing live request. Any future resumption must retain this no-repeat rule.

## Mandatory pre-deployment safety gate

The October 31 owner instruction explicitly applies the HTTP 500–599 rule site-wide, not only to collection imports. All application-controlled browser requests must use `safeFetch`/`safeImportFetch`; all server outbound HTTP must use `guardedUpstreamFetch`. KV access must use `noRetryKv`, never a new default SDK client. Do not bypass failed-request blocks through a page reload, scheduled retry, notification channel, account change or force flag.

`npm run build` must run its `prebuild` request-boundary audit and offline 5xx regression suite before compilation. Vercel's repository build command is `npm run build`. A failing audit/test blocks deployment. Never skip these checks, deploy stale/prebuilt output from before the guard, or treat a successful mock test as permission for a live repeat. Hosting/browser-managed asset requests and an unavailable control plane have explicit limitations; do not claim application code controls them universally.

Known failed live operation: the daily-packs-boosts worktree's UFC home-day schedule query (`/home/ufc/day`, tested day `2026-10-30`) returned 500 repeatedly during October 30 live Boosts checks. Do not rerun that query or the all-sport/forced Boosts operation that includes it. See the cross-worktree follow-up in the shutdown record. Diagnose from those saved records only.
